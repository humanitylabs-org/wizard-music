# Music HTTP / MCP contract (0.2.0-test.23)
The Wizard authenticated gateway is the authorization boundary. Never publish the app port directly; it has no user login. Host/Origin allowlists prevent browser cross-origin access but are not authentication. The hub additionally requires a bearer token; only the server adds it.

- `GET /health`: app process and configuration only, not backend health.
- `GET /wizard-music/api/status`: same status, no secrets.
- `GET /wizard-music/api/view/switches`: which app switches are on (`{switches: [{id, on}]}`), for the page itself; read only. Owners change them at `/api/switches` (wizard.app-switches/1).
- `GET /wizard-music/api/home`: `{settings:{online:boolean},sources,vibes,liked,recent,library,taste}`.
- `GET /wizard-music/api/liked`: `{tracks}`, every liked song, newest like first (home's `liked` is a 30-song preview). On for everyone since wizard-music#72 (was the `liked-view-all` switch, wizard-music#63).
- `GET/POST /wizard-music/api/settings`: read consent or persist `{online:true|false}`; default off, revocation cancels downloader and gates every new outbound request.
- `GET /wizard-music/api/search?q=...`: `{tracks:[...]}` (200-character query limit).
- `POST /wizard-music/api/catalog` with exactly `{"video_id":"<11-char YouTube ID>"}`: connected-account metadata lookup, independent of playback authorization but gated by the same online consent. Returns `{provider:"youtube-music",catalog_source:"youtube-data-api",items:[{id,title}],audio_verified:false,playback_entitlement:false}`; an empty `items` means no match. Rejects account, URL, operation and query selectors. `409 capability_denied` means no owner-approved Music binding; `409 reauth_required` requires reconnecting Google. `503 catalog_not_configured`, `502 catalog_auth_failed` and `502 catalog_unavailable` distinguish absent config, invalid adapter authorization and upstream failure. No caching or anonymous fallback for this call. No account list, tokens, streams or playback rights are returned. The server alone adds `MUSIC_ADAPTER_TOKEN` to the fixed Connectors `/service/music/catalog` path; incoming Authorization/cookies are never forwarded. Gateway owner authentication remains mandatory.
- `GET /wizard-music/api/account-library/status`: `{state,connect:"/wizard-youtube-music/",limit:100,error?}` from the YouTube connector’s advertised account-library capability. States include `connected`, `signed_out`, `needs_attention`, `off`, `unsupported`, `unavailable`. This status is independent of anonymous playback readiness.
- `GET /wizard-music/api/account-library/playlists?limit=100`: status plus `playlists:[{id,title,count?}]`.
- `GET /wizard-music/api/account-library/likes?limit=100` or `/account-library/playlist?id=<playlist-id>&limit=100`: status plus normalized Music `tracks`. Valid playlist IDs are 1–160 ASCII letters/digits/underscore/hyphen. Limits clamp to 1–100, invalid values return 400. The connector currently offers no continuation, and the UI explicitly describes this bounded view. No playlist URL or arbitrary source selector is accepted. Library reads return 409 when account verification is required, 503 for offline/missing/old/failed connectors, with sanitized actionable errors; status returns 200 with its state. Online consent gates all connector reads. UI queues these exact tracks (Play all or selected position), not an unrelated radio station. Playback uses the existing source and is not guaranteed by login.
- Account library is read-only: YouTube liked songs are separate from Music’s local thumbs/taste, with no generic preferences sync claim. `music_account_library({kind:"status"|"playlists"|"likes"|"playlist",id?})` exposes the same bounded read via MCP; no account credentials or browser playback side effects.
- `POST /wizard-music/api/scan` with `{}`: rescan own mounted library, `{tracks:number}`.
- `POST /wizard-music/api/station` with `{trackId:"lib:<id>"}` or `{query:"...",label:"..."}`: `{tracks,station}`. Library stations stay local; online stations require opt-in.
- `GET /wizard-music/api/station/<16-hex-id>/more?n=10`: station continuation.
- `POST /wizard-music/api/play` with `{said:"play ..."}`: resolves a request into tracks, does not start browser sound.
- `POST /wizard-music/api/feedback` with `{id,action,upcoming?:[id]}`: action `like|unlike|dislike|played|skipped`; `{ok,track,drop,learned}`. Likes/history persist in `/data/hub.sqlite3`.
- `GET|HEAD /wizard-music/stream/lib:<20-hex-id>` (or `yt:<video-id>`): audio bytes, Range/206 supported; `art/<id>` for thumbnail. The app server always adds (wizard-music#46, progressive play) `X-Wizard-Music-Live: 1` to `yt:` stream requests: the hub asks the connector for `?live=1` and answers once the first 64 KiB are on disk, with the song's full size; bytes not downloaded yet are sent as they arrive (a seek ahead waits for them), and the song keeps its downloaded bytes (no plain-MP4 rewrite) until no live player has asked for it for 30 minutes.

Track: `{id,title,artist,album,durationMs,source,art,stream,liked}`. All media/continuation URLs are rewritten to `/wizard-music/`; no bearer token is returned. Browser uses same-origin cookies at the gateway. Requests to undeclared API routes return 404. Missing backend configuration returns 503; unreachable source returns 502. A 200 health response never proves playable media.

Hub routes are the same **without `/wizard-music`**: `/api/home`, `/api/search`, `/api/scan`, `/api/station`, `/api/play`, `/api/feedback`, `/stream/<id>`, `/art/<id>`. Hub JSON originally uses `/wizard/music/` URLs; the web proxy rewrites them. `/health` is unauthenticated, all other hub routes require `Authorization: Bearer <recipient token>`.

`POST /mcp`: stateless JSON-RPC streamable HTTP (JSON response mode), initialize, ping, tools/list, tools/call. Read-only tools `music_status`, `music_home`, `music_search({query})`, `identify_list`, `identify_get({id})`; explicit writes `identify_retry({id})`, `identify_confirm({candidate_id})`, `identify_discard({id})`, `identify_restore({id})` require owner intent. Same gateway security as HTTP. No SSE stream is offered; GET returns 405. Initialization negotiates the baseline 2024-11-05 protocol. Browser playback is not an MCP-side effect.

Finished unmatched captures support POST `/wizard-music/api/identify/captures/{UUID}/discard` and `/restore` with JSON `{}`. These idempotent writes return 200 plus the stored capture; malformed UUID is 400, absent capture 404, non-`no_match`/busy or other ineligible retention state 409. Discard changes only `retention_state` to `discarded` and `updated_at`; restore sets `active` on the same record. GET `/captures` excludes discarded rows durably; GET `/captures/{UUID}` and audio remain available. Retry of a discarded capture is 409 until restored. No audio, attempts or candidates are deleted and no generic `archived` retention eligibility is introduced. See `docs/unmatched-discard.md` for behavior/retention boundaries and focused acceptance.

## Song playlists (wizard-music#39)

Wizard-owned playlists of single songs, stored in the hub's `song_playlists` table: `{id, name, description, trackIds, count, createdAt, updatedAt}`, ordered track ids (`yt:*` and `lib:*` that Music already knows; a song appears once). Nothing is written to a YouTube account.

- `GET /wizard-music/api/song-playlists`: `{playlists:[...]}` (no tracks). `GET .../song-playlists/<id>`: the playlist plus `tracks` in order.
- `POST .../song-playlists` `{name, description?, trackIds?}`: create. `POST .../<id>` `{name?, description?, trackIds?}`: rename, describe, or set the full order. `POST .../<id>/add` `{trackIds, position?}`, `POST .../<id>/remove` `{trackIds}`, `POST .../<id>/delete` `{}`. Writes answer the stored playlist plus `skipped` (ids Music does not know); bad input is 400, an unknown playlist 404. Name 1-100 characters, description up to 500, at most 500 songs.
- MCP: `playlist_create({name, track_ids, description?})`, `playlist_add_tracks({id, track_ids, position?})`, `playlist_remove_tracks({id, track_ids})`, `playlist_update({id, name?, description?, track_ids?})`, `playlist_get({id})`; `playlist_list` also returns `songPlaylists`. Every write is read back with GET and returns `{playlist, skipped}`.
- Page: Home → Your playlists (New playlist, open one to Play / Shuffle in order through the player queue, Rename, Delete, move songs up or down, remove a song); a ＋ Add to playlist button on search results and in Now Playing.
